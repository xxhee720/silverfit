# 데이터 구조와 접근제어

## 데이터 모델

| 테이블         | 목적 / 연결                                                                             |
| -------------- | --------------------------------------------------------------------------------------- |
| profiles       | auth.users와 1:1, 이름·신청자 맥락                                                      |
| admin_users    | 별도 운영자 권한, SQL/service_role만 관리                                               |
| applications   | 소유 계정, 실제 사용자의 최소 정보, 제품, mm 치수 JSON, 환경, 동의 버전·시각, 현재 상태 |
| attachments    | 신청 ID, 비공개 사진 경로·원래 파일명                                                   |
| designs        | 신청 ID, 증가 버전, 파라미터 스냅샷·스키마 버전, 생성기, 설계 파일 경로                 |
| print_jobs     | 신청 ID, 정확한 설계 ID, 실제 출력물 ID, 소재·장비·조건·시간·결과                       |
| safety_reviews | 정확한 출력물 ID, 시험 방법·근거·전문가, 기록자, 순서                                   |
| status_events  | 이전/다음 상태·이유·행위자·시각, 변경 불가 이력                                         |
| feedback       | 신청 소유자의 만족도·의견·사용 중 문제 여부                                             |

치수는 `mobility-v1-mm` 규격으로 저장합니다. 제품별 키와 허용 범위를 클라이언트 Zod와 DB 제약 모두 확인합니다. 허용 범위는 입력 오류 방지용이며, 제조 가능 범위나 안전성 기준이 아닙니다. 직접 측정과 전문가 검토가 필요합니다.

현재 설계의 `parameters`는 등록 당시 신청 치수의 스냅샷입니다. 설계 파일은 수동 등록합니다. 자동 CAD/STL 생성은 구현되지 않았습니다. 후속 작업자는 신청 파라미터를 읽어 별도 샌드박스 워커에서 CAD를 생성하고 설계 파일을 업로드해 같은 버전 등록 RPC를 호출합니다. `generator`·`parameter_schema_version`을 확장하고 생성기 버전, 소재 프로파일, SHA-256, 단위·템플릿 버전을 추가하는 마이그레이션을 적용할 수 있습니다. 생성 완료가 안전 승인으로 이어져서는 안 됩니다.

## 접근제어

- 인증은 Supabase SSR 쿠키와 서버 `getUser()`로 확인합니다. 세션 정보만 신뢰하지 않습니다.
- 공개 환경변수에는 publishable/anon 키만 사용합니다. 서버 액션도 사용자 세션 클라이언트로 호출합니다.
- 모든 업무 테이블 RLS 활성화, 익명 권한 없음. 신청 소유자 또는 admin_users에 등록된 운영자만 조회합니다.
- 일반 사용자의 직접 상태 업데이트·설계·프린트·검토 기록 수정/삭제 불가. 추가 작업은 권한 확인 RPC로만 수행합니다.
- 본인/보호자/복지사는 모두 같은 소유자 격리 원칙을 사용합니다. 계정 역할을 관리자 권한으로 연결하지 않습니다.
- 사용자 프로필 metadata에 `admin`을 넣어도 서버 가입 트리거가 `self`로 제한합니다.
- 비공개 두 버킷: `application-photos` (10MB, JPG/PNG/WebP), `design-files` (20MB, octet-stream).
- 경로 첫 요소는 신청 UUID. 스토리지 정책에서 해당 신청 접근권한 확인. 설계 업로드는 관리자만 가능.
- 원본 덮어쓰기와 삭제 정책을 제공하지 않아 일반 사용자·관리자 API로 승인 근거를 바꿀 수 없습니다.
- `/files/[id]`에서 레코드 RLS 검사 후 60초 서명 링크 발급. `Cache-Control: private, no-store`. 링크 소지자는 만료 전 조회할 수 있으므로 공유하지 않아야 합니다.
- 로그에는 연락처·사진·JWT를 남기지 않습니다. 인증 응답은 캐시하지 않습니다. Next 서버 액션의 동일 출처 보호를 사용합니다.

## 승인 무결성

설계 추가·출력 등록·검토 등록·상태 전이·사고 신고 RPC는 동일 신청 행에 `FOR UPDATE` 잠금을 잡습니다. 동시 새 버전 등록과 승인 사이의 경쟁을 직렬화합니다. 버전 unique 제약도 적용합니다.

현재 버전 → 완료된 출력 → 최신 검토 통과 → 이후 사고 신고 없음일 때만 승인 가능합니다. DB 함수 `approved_print`로 판단합니다. 임의로 프런트엔드 화면을 바꿔도 DB에서 차단합니다. 반환된 출력물 ID와 최신 검토 이력으로 실제 전달 대상 출력물을 식별해야 합니다.

설계·출력·검토 원본은 변경할 수 없으며 새 기록을 추가합니다. 부적합은 이전 통과 기록을 대체하고, 설계 변경은 이전 출력물의 승인을 무효로 합니다. 사고 신고 후에는 새 시험·검토 기록이 있어야 다시 승인할 수 있습니다.

## 한계

관리자는 모든 리빙랩 신청을 조회하는 단일 기관 MVP입니다. 기관별 격리가 필요해지면 organization_id와 담당자 배정 테이블을 추가하고 RLS를 확장해야 합니다. 예약, 결제, 프린터 제어, 자동 생성, 자동 알림, 전문가 별도 로그인·전자 서명, 사진 EXIF 제거는 제공하지 않습니다. 사진 EXIF 위치 정보는 업로드 전에 제거하도록 운영 절차에 포함합니다.
