# 운영 시작과 점검

## 운영 전 실제 Supabase 확인

별도 시험 프로젝트에서 마이그레이션 후 아래 항목을 확인합니다. 테스트 엔진의 통과만으로 실제 Auth/Storage 연동 완료를 주장하지 않습니다.

1. 사용자 A/B와 운영자 계정을 만들고 이메일 확인·로그인·로그아웃·비밀번호 재설정을 확인합니다.
2. A가 각 품목을 신청하고 필수 mm 치수, 대리 신청 구분, 동의 버전·시각이 저장되는지 확인합니다.
3. A 사진 업로드 → 상세 링크 조회. B 계정으로 A 신청 URL과 스토리지 경로를 요청하면 접근 불가인지 확인합니다. 비로그인도 접근 불가여야 합니다.
4. 10MB 초과·지원하지 않는 사진, 20MB 초과 설계, 관리자 외 설계 업로드가 차단되는지 확인합니다.
5. 운영자가 단계별 전이하고 현재 버전 설계 파일을 등록합니다. 안전 기록 없이 승인·전달하려는 시도가 실패해야 합니다.
6. 실제 시험용 출력물, 시험 프로토콜·합격 기준, 수치 결과·보고서 참조·전문가 검토를 기록합니다. 통과 기록 후 승인·전달합니다.
7. 새 설계 등록 시 승인 철회, 부적합 추가 시 재검토, 사용자 사고 신고 시 재검토를 확인합니다. 사용중단·회수 연락 절차를 수행합니다.
8. 모바일 360px, 390px, 데스크톱, 키보드 이동·200% 확대·스크린리더 라벨을 점검합니다.
9. SMTP 메일 도달, Supabase Auth 요청 제한과 CAPTCHA, 관리자 강력한 비밀번호·MFA 요구를 설정합니다. 앱에 별도 MFA 승격 검증은 없으므로 필요한 경우 Supabase 정책을 확장합니다.
10. 백업/PITR 또는 주기 백업, 장애 시 복구, 운영자 연락 담당·동의서·보관 정책을 확정합니다.

## 제작 기준

코드의 치수 입력 범위는 안전 시험 기준이 아닙니다. 경사로·팁의 하중·접지·내구성·설치 안정성·소재 적합성과 사용 환경별 시험 기준은 담당 전문가가 정해야 합니다. 시험 근거를 기록한 정확한 출력물을 전달하고 식별 라벨(출력물 UUID 앞 8자 + 설계 버전)을 부착합니다. 시험 실패품과 미검증품은 보행 사용에 제공하지 않습니다.

현장 측정 기록을 확인한 뒤 설계 파일에 반영합니다. 신청 치수 자체를 고칠 편집 화면은 없습니다. 잘못 접수된 치수는 신청을 제작 불가로 종료하고 사용자가 올바른 치수로 재신청하도록 합니다. 원본 접수 내용이 바뀌지 않아 이력 추적이 가능합니다.

자동 SMS·이메일 운영 알림은 없습니다. 담당자는 대시보드의 안전성 검토 대기와 문제 신고를 매일 확인하고 중단·회수 연락을 수행합니다. 조사 결과를 새 검토 기록에 남깁니다. 후기의 수치 만족도와 사고 여부는 운영자 조회에 포함됩니다.

## 개인정보 처리·삭제

MVP 동의서의 기본 보관기간은 참여 종료 후 1년입니다. 실제 수집 전에 운영 기관의 책임자, 연락처, 동의 철회 접수 창구를 참여자에게 별도 안내하고 필요하면 동의 문안을 새 버전으로 수정합니다. 원본 과제 자료를 수정하지 않습니다. 사진은 손·제품·설치 환경 중심으로 얼굴·주소·EXIF 위치를 제외합니다.

삭제를 사용자가 임의로 수행하면 안전 근거가 사라질 수 있어 앱에 삭제 버튼을 두지 않았습니다. 권한 있는 운영자는 동의 철회·보관 만료 시 백업 정책까지 검토한 후 아래 순서로 관리 도구에서 삭제합니다.

1. 대상 신청 UUID 확인, 삭제 사유·처리 일시를 개인정보가 없는 별도 운영 기록에 남깁니다.
2. 서비스 역할 전용 관리 도구에서 두 비공개 버킷의 해당 신청 UUID 폴더 원본 파일을 삭제합니다. 앱에 서비스 역할 키를 넣지 않습니다.
3. SQL Editor의 트랜잭션에서 아래 순서로 해당 신청 데이터만 삭제합니다. `APPLICATION_UUID`를 확인한 값으로 바꿉니다.

```sql
begin;
delete from public.feedback where application_id = 'APPLICATION_UUID';
delete from public.status_events where application_id = 'APPLICATION_UUID';
delete from public.safety_reviews where application_id = 'APPLICATION_UUID';
delete from public.print_jobs where application_id = 'APPLICATION_UUID';
delete from public.designs where application_id = 'APPLICATION_UUID';
delete from public.attachments where application_id = 'APPLICATION_UUID';
delete from public.applications where id = 'APPLICATION_UUID';
commit;
```

4. 모든 신청이 삭제된 계정의 삭제 요청은 Auth 관리 API/Dashboard로 처리합니다. 다른 신청을 기록한 관리자 계정은 FK로 삭제가 제한되므로 먼저 기록 귀속·보관을 검토합니다.
5. 삭제 결과와 백업 만료일을 확인합니다. 이 보관 만료 작업은 자동 실행되지 않으므로 정기 운영 일정에 등록합니다.

업로드 후 DB 저장이 실패한 미참조 파일은 attachments.path와 designs.path의 참조 여부를 대조하고, 충분한 유예기간 이후 서비스 역할 관리 도구로 삭제합니다. 승인 근거가 참조하는 파일은 삭제하지 않습니다.
